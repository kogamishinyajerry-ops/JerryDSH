01

身体构造：微内核与"可替换器官"

难度 ●●○

为什么这套系统拆成了几十个小包，而不是一个大程序。

一句人话：身体有一个小小的"心脏"（谁都必须有），其余全是可替换的器官——肺换成人工肺、腿换成轮子，人还是那个人。

心脏：六个核心包 源码

任何 DSH 组合都一定启动这六个包，它们构成一条主干：

📖session 会话日志那本只往后写的日记（03 章主角）
🧩system-prompt 提示词组装每次思考前拼装"给脑子的说明书"（06 章）
🛠️tools 工具注册表几十种工具的登记处与执行流水线（08 章）
🤖agent 代理句柄对"一个正在干活的 AI"的编程接口
🔄agent-loop 驱动循环心脏起搏器：想→做→记的风车（02 章）
🏷️scope 作用域让每个 AI 只看见自己该看见的能力

器官：能力 seam（接口三件套）

除了心脏，每项能力都做成一个 seam（接缝）——一个抽象接口配三种角色：定义（接口本身）、提供方（真正干活的实现）、消费方（通常是一个面向模型的工具）。想换实现，只换提供方，别的都不用动（源码）：

  • 文件系统 ctx.fs → 本地实现 ↔ 未来的远程/沙箱实现
  • 命令执行 ctx.shell → bash ↔ PowerShell ↔ 受限执行器
  • 模型对话 ctx.llm → DeepSeek ↔ pi-ai 网关 ↔ 任何新模型
  • 进程围栏 ctx.sandbox → macOS Seatbelt / Linux Landlock·bwrap / Windows ACL
  • 子代理 ctx.subagents → 进程内 ↔ Codex ↔ Claude Code（10 章）
  • 会话持久化 / 会话检索 / 压缩 / 日程 / 目标 / 技能 / MCP 桥……共 14+ 个

妙处：文件系统和命令执行共享同一个"执行世界"，把两者的提供方一起指向远程沙箱，就等于把 Bash、终端、代码补全整体搬去了云端——不需要为每个工具单独改造。

身体的两种出厂形态

  • Web 版（base + web-app 组合包）：你现在看到的图形界面就是
  • headless 版（base + headless）：无界面的命令行形态，跑脚本/CI 用
  • 两种形态之上再叠 profile（个性化配置包）和插件——层叠规则见 11 章
冷知识：插件怎么做到"不改源码也能加新事件类型"？
TypeScript 的 declaration merging（声明合并）：插件对着别人拥有的类型表说"我再往里添一行"，编译后就像原生的一样。系统里六张最重要的"类型表"（消息块、结束原因、轮次原因、会话事件等）全都开放这种扩展。
冷知识：所有跨包传的编号都是"防拿错"的
会话 id、工具调用 id、任务 id 在类型层面互不可换——就像药瓶、奶瓶、胶水瓶虽然都是瓶，但盖子拧不到一起去。历史上曾因为"任务 id 和会话 id 长得一模一样"差点出安全 bug，于是全部上了"品牌化类型"。
02

核心循环：想一步，做一步，记一笔

难度 ●●○

你发一句话之后，身体里转起来的那个风车——以及"中途插话"去了哪。

一句人话：像你解大题：读题→打草稿→用工具→检查→再想下一步。一步 = 调用一次 AI 模型 + 它顺手做的几个工具；一轮 = 从收到消息到它认为干完，中间可以有很多步。
turn/start  ── 轮次开启（领取输入之前）
   │  认领收件箱：全部 next-step 输入 + 一条 next-turn 消息
   │  组装：提示词段落 + 工具 schema
   ▼
agent/pre-step ── 串行拦截链：可 reject / 可改写消息批次
   │  首次被拒或改写为空 → 仍关闭一个无步骤轮次（尝试照样入日记）
   │  enter(messages)
   ▼
step/start
   │  entered 消息 → user/message 入日志
   │  从日记派生模型历史（03 章投影规则）
   │  agent/request → llm/stream ── 请求内幕见 06 章
   │      assistant/chunk* → assistant/message
   │  tool/call* → 六道关工具流水线（08 章） → tool/result*
step/end
   │  工具还欠请求 / next-step 输入到达 → 认领 → 下一个 step
   ▼
agent/turn-stopping ── 串行事件：轮次没有工具/插话后续时
turn/end  ── 七种终态之一（下表）

收件箱：三个投递通道 源码

你的话（以及系统的各种注入）先进"收件箱"再被认领。收件箱分两个格子：next-turn（下一轮）和 next-step（下一步）；三个通道语义精确不同：

通道落点会唤醒吗典型来源
followup 整轮排队next-turn 列表，独占自己的轮次✅用户发的新消息、给子代理的新指令
steer 中途引导运行中→最近的步骤边界；空闲→开新轮✅运行中的纠正/补充（被拒的步骤会让它先停在收件箱）
inject 静默注入收件箱里静静躺着，等别的消息唤醒❌文件变化通知、定时任务结果、技能内容等"模型可见上下文"

收件箱本身就是持久投影：每一条排队/认领/丢弃都写成规范化的日志事件，重开后队列原样恢复。认领（claim）= 一步领取"全部 next-step + 一条 next-turn"，以纯删除完成、不发丢弃通知。

轮次的七种死法 源码

终态含义谁发出
completed正常干完循环
aborted被取消打断（日志只记粗粒度；"谁取消的"是运行时信息，另走事件）循环
blocked被拦截链挡住循环
error失败（结构化错误对象入日志）循环
max-tokens轮内任一步被截断 → 整轮优先记截断，即使之后继续干了循环
interrupted崩溃后重开时合成的"补句号"——循环永远不会发这个崩溃恢复
legacy导入旧记录时取消原因不明导入器

其它拦截点与杂项 源码

  • 请求失败恢复：失败步骤关闭后、轮次关闭前，监听器可修复状态并返回 retry 开新轮——与 06 章的重试层配合。
  • 维护任务：完全空闲时可跑"非轮次任务"（比如 07 章的手动压缩），对外状态仍显示空闲。
  • 取消收敛闩：取消进行中到达的新消息会先停车，等取消完全收敛到空闲后再发车，绝不半路追尾。
  • 会话起点四来源：startup / resume / clear / compact——刷新、恢复、清空、压缩后都会走一遍"开场"。
  • 一人一份所有权：编程创建的代理返回"句柄+拆除器"——只有创建者能拆，工厂卸载会连带停掉它造的所有代理；组装到一半失败会整体回滚，"半组装的 AI"在类型上不可到达。
03

日记本：只许往后写的会话日志

难度 ●●○

整套系统的记忆中枢——一个听起来很"笨"、实则极其聪明的设计。

一句人话：一本只许往后写、不许涂改的日记：你说的、AI 想的草稿、每次工具申请和结果，全部按顺序编号记下。想"后悔"只能再写一行新的，不能撕旧的。

为什么这么设计

🎬可以重放从第一页读到最后就能完整重现整场对话，包括 AI 的每个念头（草稿碎片也不丢）
🔋断电不慌最后一行写了一半？撕掉那半行，系统自动"补句号"接着来
🔒不可篡改历史就是历史；所有"当前状态"都是从日记算出来的投影

日记里都记什么：事件词汇表 源码

每一行叫一个事件，全局连续编号（第 i 行的编号就是 i）。核心 12 + 2 种，插件还能扩展：

事件记录什么模型可见？
turn/start · turn/end轮次的开/闭（含七种终态）否（结构）
step/start · step/end步骤边界否
user/message用户消息 / 注入上下文 / 续跑请求（来源字段区分）✅
assistant/chunk流式草稿碎片——逐 token 保真，绝不丢弃否（原料）
assistant/message组装完成的正式回答（带 token 用量；截断的前缀会标 interrupted）✅
tool/call · tool/result工具申请（参数原样字符串）与结果（可带展示卡片数据）✅（结果）
steering/message中途插话✅
todo/write任务清单整表快照（最新一次赢）否（界面）
request/header请求信封全量快照（配置+系统提示词+工具表），变更时追加否
request/context路由与容量变化（仅变化时记）否
session/end-seed"继承的前缀到此为止"——恢复/分叉的边界标记否
插件扩展压缩三事件、钩子对、子代理描述符……都是"仅日志"事件视声明

遮住 ≠ 撕掉：surface（模型可见层）源码

模型看到的对话不是日记全文，而是日记的一个投影（surface）。三种产生消息的事件带一个"怎么进入投影"的标记：普通的 append（排在尾部），以及压缩用的 replace(start, end)（原位替换一段、旧页全部保留，只是模型暂时看不见）。派生规则：

  • 草稿碎片在派生时跳过——组装后的正式回答才是权威；
  • 内容为空的回答（截断且没写出东西）不进对话，但用量照记；
  • 工具结果转成 user 角色消息；注入上下文按时间顺序原样插入；
  • 边界类事件（轮次/步骤/请求头）都是结构信息，不产生消息。

铁律："模型可见即已记录"是运行时断言的不变量——凡是发给模型的东西，必须能从日记完整重建。所以想新增一种模型可见的输入，就必须新增一种事件类型，没有捷径。

家谱与身份证 源码 + 实测

  • 每本日记的首页（header）记元数据：格式版本、创建时间、工作目录、父会话（从谁分叉）、继承长度、辈分（嵌套深度）、所用的能力预设。辈分会持久化，重开也降不了——防"套娃"。
  • 分叉（fork）有讲究：只能从"已完成轮次的平衡点"分叉，正在写一半的轮次不带走。
  • 会话编号没有统一格式——本机实测就有两种长相（115 个裸 UUID / 87 个 session- 前缀 UUID，来自 6 个不同的出生地）。判断会话身份要看首页字段，永远不要猜编号长相。
  • 所有事件数据必须在写入时就可通过 JSON 序列化检查——坏数据在源头就被拒，日记永远和磁盘格式一致。
04

落盘：两个存储后端的较量

难度 ●●●

日记在磁盘上长什么样——以及为什么最新最炫的数据库方案反而没当默认。

一句人话：日记默认存成压缩文件（像羽绒服抽真空）；8 月那次大优化把"数据库方案"瘦身了 89%，但工程师拿数据一比——传统文件反而更小，于是数据库仍是可选项。不迷信新技术，拿数字说话。

磁盘布局 实测

默认后端：JSONL + zstd 源码

  • 物理形态：一个只含首页的校验帧 + 之后每批写入一个带校验的 zstd 帧——"真空袋按批封装"，断电时最坏丢最后一袋。
  • 打包行：AI 回答时一个字一个字蹦的碎片，连续 3 个以上同类型的会被打包成一行再存（三种打包标签），真实编程会话日志实测小 60%；读取端永远解包，写读不对称但无感。
  • 攒批写入：事件先进队列，固定 200ms 合并窗口（后来的不延长截止），每轮领取前强制排空——一次磁盘同步扛更多记录，一条不丢。
  • 懒实体化：create 不写盘！第一次真正写入才落盘（临时文件 + 强制同步 + 硬链接发布防覆盖）。创建了但一个字没写的会话不留任何痕迹，也不出现在列表里。
  • 没有删除接口：日记只增不减，清理靠手动删目录；同一本日记同时只允许一个写入者。

可选后端：SQLite（schema 17）源码

8 月 19 日版本带来的重做：把碎片流打包进数据库行——每行最多 1024 个事件 / 1MiB，超过 4KiB 的走 zstd 压缩，引用序列用差分编码；每批事务 BEGIN IMMEDIATE + 同步级别钉死 FULL（不同 SQLite 构建都保证已提交就真落盘）；已提交的行永不重写（写放大有界）。旧格式数据库一律拒绝、不提供迁移。

崩溃恢复的精细账 源码

  • 最后一帧撕裂 → 保留已完整解码的记录、从帧头截断、合成"补句号"；已提交前缀里的校验失败才算损坏（拒绝加载）。
  • 被打断的工具调用恢复成两种语义：TOOL_NOT_STARTED（没开始，随便重试）和 TOOL_OUTCOME_UNKNOWN（结果不明——明确叮嘱模型只重试幂等操作或先问人）。
  • 拒绝外来格式是明确报"请升级"而不是报"损坏"——版本方向说清楚，不吓唬人。

外部工具不能裸读日记文件（压缩帧 + 打包行 + 未来可能是数据库行）。正确入口是官方读接口：列清单 list / 整本读 inspect / 从水位增量读 readFrom(seq)——最后这个是所有"加速小抄"的地基（05 章）。

05

小抄体系：投影与缓存

难度 ●●●

聊天列表页为什么不用翻整本日记？——因为有一套"小抄"加速层。

一句人话：日记是权威，其余全是小抄。小抄的铁律：可以过期，绝不允许错。写失败了就先放着（下次自愈），对不上号就整张扔掉重算——日记永远是小抄的老板。

投影：从日记自动算出的"当前状态" 源码

框架订阅一次"日记有新事件"，之后每个事件都流经每个注册的计算单元（标题、token 用量、目标进度……）。两条省力规矩：

  • 同引用即无工作：与本单元无关的事件，计算函数返回同一个对象引用，系统用"是不是同一个对象"一比就跳过全部下游工作；
  • 全量值规则：凡是带状态的事件必须带"变更后的完整状态"，绝不带增量——每个值自己就能说明自己。

本机实测注册的单元：sessionStats / title / goal / tokenUsage / contextPressure——正是界面侧栏和会话卡片上那些数字。实测

持久小抄：检查点缓存 源码

重开后重算所有状态太慢，于是每本日记在轮次结束时存一份检查点到 session_projcache.json。安全契约六条：

  1. 后台写失败只警告，缓存保持旧（下次自愈）；
  2. 计算单元版本号变了 → 整行丢弃重算，绝不做迁移；
  3. 存下的值必须过当前的校验器，畸形行直接扔；
  4. 记录绑定日记身份（创建时间+目录）——同编号但"换了本"的记录整体作废；
  5. 日记领先，小抄跟随：先把事件刷进日记，小抄才落地——崩溃时小抄只会落后，不会超前；
  6. 两个必写点（轮次结束、会话转冷）+ 条数/时间双节流。

冷读阶梯（打开旧会话时）：查小抄 → 找到可信水位 → readFrom(水位) 只回放尾巴 → 刷新小抄。这就是第 04 章 readFrom 存在的意义：增量折叠只补尾巴。

会话搜索：默认关着的全文索引 源码

  • 官方自带基于 SQLite FTS5 的全文搜索（分词召回、跨会话分页、高亮摘要），但默认 openAt: never + 纯内存——连数据库模块都不加载，搜索请求直接报"未启用"。侧栏只能搜标题和项目名。
  • 想用要在配置层改 openAt: first-search / startup 并给持久路径；索引是"可丢弃重建"的派生库，单进程独占，绝不能指向日记数据库本身。
  • 索引默认覆盖三层文本：当前可见的、被压缩遮住的、纯日志的——遮住≠删掉，历史永远可搜。

为什么值得知道：第三方"会话搜索/记忆"类插件很多，但官方引擎其实内置只是没开——先开官方的再决定要不要装插件，是省钱省事的最短路径。推断

06

与模型说话：请求装配 · 缓存纪律 · 流式协议

难度 ●●●

"想"这一步的完整内幕——系统如何又快又省地跟模型对话。

一句人话：跟模型对话像续写一本小说：小说前面的字一个都不能改（改了 AI 就得从头重读，又慢又贵），新内容只能往后贴。整套系统有条铁律——只往后加，不往前改。

一次请求怎么拼出来 源码

  • 系统提示词：各插件贡献"段落"，按序号拼接（约定：-100 是 DSH 的自我介绍、0 是部署人格、工具说明书占 100–199）；段落里的 {{变量}} 在组装时插值（当前时间、工作目录等）。
  • 工具清单：各提供方报上自己的工具说明书，汇聚成本次请求的工具表（有个保留字防抢占）。
  • 对话历史：从日记投影（03 章派生规则）。
  • 三者组装成一次完整请求，同时把请求信封全量快照写进日记（02 章的 request/header）——"每个请求都是日记的纯函数"。

有一个霸气但合法的口子：complete 段——任何插件可以声明"我就是完整的系统提示词"，组装流程照常跑完（工具照常解析），最后恢复它为唯一段落。想整体换人格，走这个正门。

KV cache：AI 的"读到哪记到哪" 源码

模型服务端会把读过的前缀缓存住。死穴：前缀改一个字，缓存全部作废、整本重读重算钱。系统的五条缓存纪律：

✅ 常驻部分稳定
只处理新尾巴
❌ 每轮都改前缀
缓存全作废

缓存命中（不重读） 新内容 被迫重读

  1. 系统提示词与工具表只在真的变化时才记"变更快照"——连续请求前缀逐字节稳定；
  2. 会变的信息（时间/目录/文件通知）做成便利贴：完整快照追加在历史后面，旧快照被新快照"顶替"但历史一字不动；
  3. 压缩（07 章）是唯一合法的"重写"，天然断缓存——这是它的固有代价；
  4. 回放元数据跟内容块逐块对齐裁剪：丢弃哪个块，同位置的元数据一并丢——"存的东西永远描述存的内容"；
  5. 跨模型不透传：A 家的缓存状态只有同一适配器实例才认——换模型续聊，缓存作废是机制使然，系统只降级不报错。

流式协议：碎片怎么拼回文章 源码

  • 共享组装器：拼装逻辑全系统只有一份，适配器只管吐格式正确的碎片。纪律：token 用量必须在结束标记之前；已关闭块的迟到碎片直接忽略（坏适配器撑不爆内存）；被截断的工具调用一律丢弃（半截命令不能执行），同位置的回放元数据同步裁剪。
  • 中途取消：已流出的文本/思考前缀会以 interrupted 标记定格入日记——"流了什么留什么，没派发的调用不存在"。
  • 每次辅助调用（压缩摘要、会话起标题）可以带"用途"标记，适配器可据此走专用策略——普通对话不带。

适配器八条军规（接新模型的合同条款）源码

① 用量先于结束标记结束后不许再吐碎片
② 工具参数全程保持原始字符串模型给的什么样就传什么样，解析归组装器
③ 两条错误路径直接抛异常（传输错）或以 error 结束标记收尾（提供方带内错）
④ 一次调用 = 一次尝试适配器禁用底层库的重试——重试统一归上层管，不会叠罗汉
⑤ 停顿看门狗默认 5 分钟无输出强制超时，早到的用户取消保留为"已取消"
⑥ 溢出只有一个错误码上下文超限统一报 CONTEXT_WINDOW_EXCEEDED，绝不让人猜各家报错文案
⑦ 空回答 = 可重试错误不是静默成功——默认自动重试
⑧ 每个请求带应用身份头User-Agent 声明"是 DSH 在调用"，公开产品信息、无隐私

重试三层责任制 源码

层谁管默认发生什么
路由层模型路由配置普通模式重试 5 次（带退避）同一请求自动再试
代理层失败恢复监听器可修状态后返回 retry开一个新的持久轮次（日志看得出是重试）
直调层插件自己无！一次就是一次插件直接调模型必须自管重试——著名的坑

另有两道防换防：请求的"准备-派发"绑定同一代适配器注册（设置中途变了也不会"一代的能力配另一代的端点"，不匹配直接报错）；路由替换是原子操作，请求永远看不到半新半旧。

token 记账：三只互不重叠的桶 源码

inputTokens未命中缓存的输入
cacheRead / cacheWrite缓存读/写单独计（计费输入 = 三者之和）
outputTokens含思考 token（内部明细不重复算）

计量器是"回放快照"不是计数器：锚定在已消费的事件数上；只有最近一次成功请求的信封完全一致时才复用它的精确用量做锚点，否则整包启发式估算。压缩的 80% 水位（07 章）、界面的"上下文压力"条，都吃这里。

07

日记太厚：压缩（compaction）

难度 ●●○

脑容量有限（上下文窗口），日记无限增长——中间的减压阀。

一句人话：不是撕页，是贴便签遮住旧页：把早前的内容请另一次模型调用浓缩成一页摘要，贴在对话开头。旧页一页不丢，只是模型暂时看不见——想搜历史随时翻回来。
📋 摘要便签（新的开头）

灰页 = 被遮住（shadowed）——原文完好保留在日记里，替换标记记录了遮住的范围。

什么时候压、压多少 源码

参数默认含义
thresholdRatio0.8占用超过「上下文容量 × 0.8」就触发（每步请求前检查）
retainRatio0.16最近 16% 的内容逐字保留，绝不进摘要
maxTokens8192摘要调用的最大产出
compactionRetries1压完还超水位的额外再试次数
autotrue自动监听压力；关掉则只能手动
modelPolicies—可按"提供方+模型"逐对覆盖以上参数

省钱顺序也有讲究：压力超标时先跑"无模型修剪"（把超大的工具输出替换成一行摘要，零 token 成本）→ 重新测量 → 不够再请模型生成摘要。可能免费就过关。

三事件锁：崩溃也骗不了人 源码

压缩在日记里留三行：compaction/start（上锁）→ compaction/summary（摘要+遮住范围+估算 token+用了哪个模型）→ compaction/end（解锁）。锁最后释放——中途崩溃就留下"有 start 无 end"的遗留锁，一眼可检测，绝不可能出现"谎称已完成"的假标记。另有一条"继承边界"规则（03 章 end-seed）：上个生命周期留下的遗留锁视为已死，不会误伤重启后的会话。

边界纪律：替换范围永远保持"工具申请↔结果"成对（半对不能遮）；但不必保持整轮——超大轮次里较早完成的步骤可以被单独压缩。手动压缩在完全空闲的"维护相位"跑，不抢正常轮次。

08

工具流水线：从申请到结果的六道关卡

难度 ●●○

AI 说"我要读那个文件"之后发生的事——以及为什么没人能篡改它的申请单。

一句人话：工具调用像过安检：申请单一进场就塑封（谁也改不了），先问"让不让带"（可触发家长签字），再过一道只收紧不放松的终审，执行完还能被"开箱检查/替换展示"，最后盖章入册。
① 入口塑封参数冻结·非 JSON 拒收·发身份牌
② pre-execute允许/拒绝/请求审批（瀑布，可多监听器）
③ guard 终审只能再拒不能放行——权限只减不增
④ execute环绕执行；可换取消信号；并行/独占调度
⑤ post-execute验收：换展示/换值（二选一）/打回成错误
⑥ result 盖章冻结入日志；观察者只能看不能动

几条硬规矩 源码

  • 申请单不可篡改：历史、审计、界面、执行四方一致是铁律——想在半路改参数？没有这个口子。要改输入，只能在进入步骤前改"消息"（02 章 pre-step）。
  • 审批是关卡 ② 的 ask 分支：只有拿到"允许这一次"才继续，其余一律拒（09 章）。
  • 调度两态：可并行的（同时读三个文件）进滚动池；必须独占的（写文件、跑交互命令）排成顺序屏障。
  • 结果分两层：执行期的"结构化值"只活在当下（不入日志）；入日志的是给模型看的"内容 / 错误 / 展示元数据"。工具可以在展示元数据里塞自己的界面卡片（比如文件修改的 diff 卡）。
  • 两句工具黑话：deferContext 把补充说明挂到本次结果上（结果送达后注入）；concludeTurn 让"问用户"类工具在拿到结果后直接结束本轮——提问就该停下来等答案。
  • 失败不掀桌：未知工具、参数坏、执行炸——都变成结构化错误结果返回给模型（它能看到并自救），当前轮次继续。连"渲染结果失败"都会被降级成安全文本，流水线任何一层都不会把"没法展示"变成崩溃。
  • 嵌套调用有出身牌：组合工具派生的子调用带"父执行令牌"；代码模式下模型直呼原生工具名（没有父）会在进策略前就被拒——只有程序里转发的调用才能用那些内部工具。
09

安全模型：围栏、签字，和一条大实话

难度 ●●○

能删你文件的助手必须配好保险丝——两个旋钮、两层边界、一个捆绑开关，外加一条必须知道的大实话。

一句人话：保险丝有两颗：围栏（操作系统级，管 AI 能碰哪些文件）和签字（出圈前先问你）。大实话：这两颗保险丝只管 AI，不管插件——装插件等于请陌生人以你的身份进家门。

旋钮一：围栏（沙箱）三档 源码

档位文件权限说明
只读只能看，一字不能写最严
作业区可写项目文件夹 + 系统临时区默认档；文件工具与命令行共用同一套边界，不会打架
全权不设围栏直接绕过围栏系统执行；速度快，责任在你
  • 围栏是操作系统级的（macOS 安全带 / Linux Landlock·bwrap / Windows ACL），不是口头承诺；不同后端报"拒绝"的黑话不同（只读文件系统错误 / 拒绝访问 / 不允许操作），系统按方言精确识别。
  • 围栏会诚实汇报自己的完整度：老内核或 Windows 某些缺口只能"部分强制"——部分 ≠ 完整，较真场景必须当失败处理。
  • ⚠️ 围栏只管文件，不管网络——围栏里的程序照样能上网；进程可见性同样不管。
  • 文件工具有一层进程内"策略围栏"（读写检查路径），官方明说它是提醒不是安全边界——真隔离靠上面的系统级围栏。
  • 升级重试的规矩：被围栏拦下的操作可申请"只这一次更宽权限"的重试——那是一次带新策略的新调用，不是修改进行中的调用。

旋钮二：签字（审批）fail-closed 源码

AI 想出圈（比如往项目外写文件）？先来问你。你的回答只有四种，其中只有一种放行：

✅ 允许这一次只批这一件事，下次再问
❌ 拒绝不干了
↩️ 撤销问题撤回
💤 没人回答同样算拒绝——宁可不做事，不可乱做事

每次问答都成对记入日记（只入日志、不给模型看）。「一律拒绝」模式在排队发问之前就在服务内部生效——想偷偷插队塞一个自动点头器？插不进去。空闲会话的提问直接拒绝（审计必须落在轮次边界内）。

捆绑开关：权限预设 源码

预设围栏审批适合
workspace-write作业区可写询问日常默认
danger-full-access全权一律拒绝全自动可信场景（写本报告的会话正在用这套 实测）

两个旋钮也可以单独拧——单独拧出来的组合叫"自定义"，是个只读的派生态，不能当目标切换。预设服务还有个组合前提：必须配了能施围栏的执行器，否则加载即失败（不肯静默降级）。

MCP：接外部工具的标准插口 源码

  • MCP 服务器带来的工具以 mcp__服务器名__工具名 注册，和原生工具平起平坐；名字做规范化防撞车（64 字符上限 + 冲突时加哈希尾）。
  • 两种接法：stdio（在本机启动你配置的程序——和插件同级的安全责任）与 http（连远端服务）。
  • 断线自动重连有预算：连续失败 10 次就注销该服务器的工具，稳定运行 30 秒重置预算——崩溃循环的外部服务不会被无限复活。
  • 结果里的图片要成为正式附件需同时满足：附件服务在场 + 本次模型路由声明支持图片；不满足的块降级成诊断文本，绝不静默消失。

大实话：装插件 = 请陌生人进家门 源码

官方文档原话大意：安装许可的本质，是在 agent 的一切沙箱之外、于你的机器上执行这个包的代码的许可。只装你信得过的来源，并把版本锁定到具体的提交（commit）。

密码本（credentials）的 0600 权限只防其他系统用户，不防同身份的插件进程。本研究的对策：每个插件先做"源码体检"（查偷偷执行命令/外联），过检才装。实测

10

帮手体系：AI 也会"打电话叫人"

难度 ●●●

一个 AI 忙不过来时，可以派生出一整棵帮手树——甚至雇别家 AI 打工。

一句人话：帮手分两种：一次性钟点工（派个活，干完散伙）和长期管家（拉了个群，可以一直派活、催进度、按暂停）。每位管家有自己的日记本，关机了也能"冷启动"复活接着干。

两类能力，两种开门方式 源码

  • 一次性 run：提供方用静态"能力旗标"声明自己会什么（结构化输出/深度上限/工具过滤/人格）。你要它不会的？启动时就拒绝，绝不"假装接了然后偷偷不做"。
  • 可继续（continuable）：提供方实现一个特定方法就算有这能力——方法存在即能力。子代理由"继续执行管理器"统一组装，提供方只贡献"要不要带父级历史"这一点点意见，其余生命周期（创建/投递/冷恢复/拆除）全归管理器。

六种提供方（传输层）源码

提供方类型特点
spawn进程内全新子代理，不带父级上下文
fork进程内带父级已完成轮次的前缀作种子（半截轮次不带上）
dsh-sdk进程内嵌套 DSH 实例
acp协议桥Agent Client Protocol 外部客户端（可代理审批）
codex外部产品把一轮委派给 OpenAI Codex；可设非交互权限模式
claude-code外部产品同理，委派给 Claude Code

注意"继承父上下文"只指对话种子（fork 为真），不意味着继承工具、服务和权限——每个子代理有自己的能力组合。给子代理挑工具/换人格是"可见性"控制（挑了就从它的说明书里消失且拒绝执行），不是沙箱。

长期管家的生命周期 源码

状态含义收到新指令时
running正在干活直接排队（收件箱是唯一的队列）
waiting自己停稳了，但雇的下级还没收工唤醒它本人
无驻留进程里没有它（比如重启过）冷恢复：从日记重建，续跑等待中的轮次
  • 防套娃：每位帮手记"辈分"，出生就写入日记首页；可以给单次委派设深度上限，超了启动即拒。
  • 防冒充：派活/打断的权限来自"确切在线的直系父级"这一身份；消息上的"发送人"字段只是署名，不授予任何权力——班级群里没法假冒班主任点名。
  • 打断的讲究：只停"正在做的那一轮"，收件箱里排队的消息不丢（像按暂停，不是掀桌子）；对不存在/已收工的目标打断是合法的空操作。
  • 指令的取消权只到收件：消息一旦被收下，调用方的取消既不会撤回它也不会拆掉子代理。
  • 汇报与记账分开记：帮手主动汇报是一种来源，系统在帮手收工时自动给家长发的"结算通知"是另一种来源——日记里的署名刻意不同，绝不把系统的话记成帮手说的。
  • 查名单三级加速：活着的问内存（零成本）→ 冷的查小抄（05 章）→ 都不行翻日记。速度全靠前面章节的投影缓存撑着。

实验性：Agent Teams（团队）源码

8 月 19 日版本新增：一组 AI 共享一块任务板（谁认领了什么、什么任务卡住谁——有向无环图 + 版本号防写冲突）和一个留言信箱（消息先存档、对方确认收货才算送达——差集就是"待送达"）。有趣的两点：任务板的"工作范围"标注只是提醒不是锁；整个团队状态存在根会话的日记里，回放日记=复活团队。官方标注"实验性"。

插件机制：层叠的饼干与三个著名的坑

难度 ●●●

生态有上万个插件仓库——但"装得上"和"装得好"之间隔着三个坑。

一句人话：插件 = 一个带"安装说明书"的 npm 包。系统像叠饼干一样组合它们：官方底座 → 各插件层 → 你的个人覆盖层——下面的层打底，上面的层说了算。

层叠顺序（下 → 上，上层覆盖下层）源码

① 官方组合包 bundles（base / web-app / headless + 各插件自带的 patch 层）
② profile 覆盖层   ~/.dsh/profiles/<名字>/cordis.patch.yml   # 某个实验场的私人定制
③ home 覆盖层     ~/.dsh/cordis.patch.yml                # 所有组合共享，优先级最高
④ 命令行临时层    --patch overlay                        # 一次性试验
  • 安装命令 dsh plugin --profile X add 包名 = 转发 pnpm 安装 + 自动把包名登记进该 profile 的 bundles。
  • 没有"安装说明书"（dsh.bundle 字段）的包也能装，但只算普通依赖，打警告、不激活。
  • 覆盖语法三种：整段替换某项配置 / 插入新行 / 禁用某行（disabled: true）；指向不存在的行只警告不报错；想禁用一整层要写"空列表"，留空文件反而报错。
  • 模块解析先查 DSH 自带的依赖、再查 profile 自己装的——所以官方子包平时根本不用装。
  • 配置各归各家：全局设置 settings.yaml（界面设置页写这里）、密码本 .credentials.yaml、插件自带数据各自目录（多数启动时读一次，改文件要重启）。

三个著名的坑 实测踩中

🏷️坑一：版本标签错位官方子包的 npm「latest」停在远古版本，新版只在「next」——手动装子包会装到石器时代。对策：显式写版本号，或干脆不装（靠内置解析）
🧱坑二：构建脚本被拦pnpm 10 默认拦截依赖的安装后构建——含原生模块的插件"装完即坏"：界面一切正常，数据默默不落盘。对策：声明构建白名单 + 手动重建
🌐坑三：网页专用插件声明"硬依赖网页服务"的插件，装进无界面组合会启动失败（缺服务，永远等不到）。对策：这类插件只装进网页版组合

坑二的典型案例：会话记忆插件 dsh-thread 装完一切正常，实际每次记事都报"找不到绑定文件"——记忆完全没落盘而表面无事。装含数据库/原生依赖的插件，装完务必验证数据真的落了盘。

怎么确认"插件真的装上了" 实测

网页版会把每个插件的"客户端代码"挂在固定路径下发。一行命令探测：

curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:端口/plugins/包名/client.js
# 200 = 客户端模块在正常下发（实测 373KB 模块正常返回）；404 = 没装上/没激活

密码本换代事件（前车之鉴）实测

8 月 21 日版本重构了密码本格式（旧"扁平表"→ 新"带版本号的结构"）。新格式写的文件，旧版本的"读证件员"读不懂——于是还停在旧版的电脑一夜之间"冷启动必挂"。这叫格式升级的单向门：门只能往前走。所幸新版本开机会自动升级旧文件。教训：别长期停在版本断代点；升级前看更新说明里有没有"凭证/存储格式"字样（12 章）。

# ② git：主干有没有新提交（官方仓库浅克隆）

研究方法：比结论更值钱的规矩

难度 ●○○

这份报告的每个数字是怎么来的。

  • 绝不碰活体：所有实验在隔离配置包（profile）和 /tmp 临时目录完成；真实使用的设置、密码本、正在运行的界面全程只读零改动。
  • 新版本先隔离试穿：/tmp 独立安装验证行为，不通勤升级全局。
  • 插件先体检后安装：源码扫描（进程执行/外部连接/数据外传）。
  • 三级证据分级，绝不混说：实测 本机亲眼所见 · 源码 读官方代码与设计文档 · 推断 合理推测并明说未实证。
  • 多源交叉：版本动态要 npm + git + GitHub Releases 三源一致才算数；存储性能引用官方设计文档的基准数据并注明。
