## 三、"给完整离线部署包就能用，对吧？"——对，但有 5 个坑

打包机（有外网）→ 目标机（内网 Windows）流程成立，本仓 FIELD-NOTES 有对应雷区：

1. **包名与 dsh.bundle 核验（F4）**：npm 与 GitHub 同名包可能是别家的/无 `dsh.bundle` 声明（装上不激活）。每个候选先读 GitHub repo 的 `package.json` 定真名，npm 只当分发渠道核对。
2. **空壳包陷阱（F10）**：GitHub 源安装按 `files` 字段打包，repo 只提交 src 没提交 lib 的，装出来是没代码的空壳（dsh-crosstalk 先例）。打包机上逐件验证主入口能 `require` 加载再进包。
3. **原生绑定跨机一致（§3.6 实录）**：dsh-thread 的 better-sqlite3 编译产物绑定 **Node ABI 版本**（NODE_MODULE_VERSION）。打包机与目标机必须**同 OS + 同 Node 大版本**（目标机 win32 ×64 → 打包机也要 Windows + 同版本 Node，或提前备好对应 prebuilt .node 塞进包）。本机 0.1.5 升级时踩过 137→127 ABI 换代。
4. **profile 整体搬运优于现场安装**：推荐**打包机组装好整个 profile（含 node_modules）整体拷贝**，目标机零安装动作。红线（F11）：**永远不要在目标机的 profile 目录里跑 npm install**——会把陈旧官方包毒进 profile 根，符号双实例导致全 profile 工具调用崩。
5. **伴生运行时随包**：Python 3.x（pdf-reader）、zagens 引擎（DSH-Office）、Hindsight 后端 + embedding 模型（hindsight，P2）全部预先落盘，`config.bin`/环境变量指向包内路径。

**打包 SOP**（复用 U 盘/离线包既有流程 + windows-offline-asset-download skill）：

```sh
# 打包机（Windows ×64，与目标机同 Node 版本）
dsh plugin --profile pkg-staging add <上述 10 件 + DSH-Office>
dsh --profile pkg-staging --dump-config   # 树完整、无 pending 服务
# dsh-plugin-gate 全量扫描包内每件插件 → PASS 才入最终包
# 整体拷贝：~/.dsh/profiles/<name> + dsh 本体 npm 离线 tarball + 伴生运行时
# 目标机
dsh --profile <name> --dump-config && 冒烟一次   # 06 §2.3 演练协议
```
